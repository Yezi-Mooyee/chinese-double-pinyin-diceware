# 05：密码管理器背景（已确认事实）

本文件记录此前查证过、与后续操作有关的结论，均来自读源码或官方文档，可以直接引用。

---

## KeePassXC

### 快速解锁（Quick Unlock）
- 只能通过系统集成实现，Windows 上依赖 Windows Hello（默认启用）
- 没有软件内短码功能，这是与 Keepass2Android 的关键差异
- 平台支持：Windows → Windows Hello；macOS → Touch ID / Apple Watch（2.8 才支持「Touch ID 不可用时改用设备密码」）；Linux → Polkit，2.8 才有
- 密码锁定后解锁：官方手册称「按回车或点击 Unlock Database 即可启动生物认证流程」（未实测）
- 首次必须用主密码完整解锁一次才能设置；系统密钥失效（改密码、增删指纹、系统大更新）后需重输主密码
- Windows Hello 包含 PIN 形式，因此无指纹的 PC 理论上可用；但 KeePassXC 的可用性检查是否接受纯 PIN，未验证，需要实测

### 版本状态
- 2.8.0-beta1（2026-09-23）是预发布版，不建议在稳定环境采用
- 2.8 的主要内容：Qt 6 迁移、远程数据库同步（通过外部命令）、Linux Wayland 自动输入、Linux Polkit 快速解锁、一批 CVE 修复
- 稳定版 2.7.12 没有远程同步功能

### 远程同步（2.8 新增，本质说明）
- 本质是给外部命令套一层 GUI 壳：用户填「下载命令」和「上传命令」，用 `{TEMP_DATABASE}` 占位
- 不做条目级合并，是整文件覆盖语义
- 官方警告（意译）：若在下载完成之后、再次上传之前远端被修改，那些改动会被覆盖。**同步不是原子操作**

### 合并（`keepassxc-cli merge`）
- 语法：`merge [选项] <数据库1> <数据库2>`，第一个文件被合并结果替换，第二个不变
- 关键选项：`-d/--dry-run`（只打印变更）、`-s/--same-credentials`、`--key-file-from`、`--no-password-from`
- 方向性：条目层面是并集（按 UUID + 修改时间择优），两个方向结果等价；差异只在数据库级元数据（保留第一个参数的）
- 默认不处理删除：`Merger::mergeDeletions()` 要求合并模式为 `Synchronize` 才执行，而根组在默认情况下兜底为 `KeepNewer`，因此 **tombstone 不生效，已删条目会复活**
- 影响面与方向无关；而且行为是保守的，只会复活，不会误删
- 规避方式：日常走覆盖路径（下载→改→上传），不走合并路径；只有两端都改过时才需要合并

### KeePassXC 的其他已确认事实
- Windows Hello 快速解锁的凭据由系统密钥库保护，绑定设备
- 没有内置的 WebDAV/SFTP 客户端（长期以来的功能请求）
- 浏览器集成有「Confirm Access 对话框」，勾选 Remember 后该站点不再询问，暴露面会随使用单调增长，需要定期用 Browser Statistics 审计并清理
- 数据库解锁状态下，浏览器集成 / Auto-Type / SSH Agent / GUI 全部可用 ⇒ 解锁时长是极敏感的参数

## Keepass2Android (KP2A)

### 快速解锁（QuickUnlock）
- 机制：校验主密码的最后 N 个字符（N 默认 3，可在应用设置调整）
- 也支持「来自数据库条目的快速解锁密钥」：若数据库根组中存在标题为 `QuickUnlock` 的条目，则用该条目密码作为解锁码
- 启用位置：解锁界面上的「启用快速解锁」复选框；默认值来自「应用设置 → 快速解锁」
- 有软件内短码，与 KeePassXC 不同

### 生物识别解锁
- 位置：设置 → 数据库 → 数据库安全 → 生物识别解锁
- 两种模式：「启用完整的指纹解锁」（主密码加密存于 Android Keystore）／「对快速解锁启用指纹解锁」
- 系统密钥失效后需重新启用

### 缓存与同步（读源码确认）
- 缓存目录：`noBackupFilesDir/OfflineCache/`（Android 5.0+），属于 Android 规范的 files 类目录，不会被「清除缓存」或垃圾清理工具删除
- 旧版遗留位置在 `cacheDir/OfflineCache/`（会被清理）
- 三个文件/库：`.cache`（内容）、`.cache.version`（本地版本哈希）、`.cache.baseversion`（基准版本哈希），均为全文件 SHA-256
- 不使用 ETag / If-Match / 条件请求，冲突检测靠下载整个文件算哈希来比对
- 同步分支：
  - 远端变了 + 本地没变 → 重新加载远端（覆盖，删除生效）
  - 远端没变 + 本地变了 → 上传（覆盖，删除生效）
  - 两边都变了 → 合并（删除可能复活）
  - 都没变 → 无事
- 每次打开、保存、同步都全量传输，没有增量。源码注释里也承认「本可以用版本号判断是否需要复制，但这样更安全」
- 手动同步入口：打开数据库 → 群组视图 → 溢出菜单 → 「同步数据库…」/「仅使用本地缓存」/「缓存副本同步至文件源」
- 应用设置里的「文件操作」只有行为开关，没有动作按钮
- 「清除缓存」功能在 UI 中找不到入口（`ClearCache()` 方法存在但无界面），需要清理时只能「清除应用数据」

### 内置键盘（「单行键盘」/简易键盘）
- 布局 `kbd_kp2a.xml` 只有一个 Row：ABC / 用户名 / 密码 / `>` / KP2A 图标 / 退格 / 回车 / 锁定
- 开关：应用设置 → 键盘 →「输入凭据设置」→「简易键盘」
- 键盘切换：默认需手动切；KeyboardSwap 插件可实现自动切换（需 ADB 授权一次，不用 root）；「键盘切换回退」「完成后切换回来」用于切回

## keyfile（密钥文件）

- 是复合主密钥的可选组成部分：`密码 + keyfile + 硬件密钥`
- KeePassXC 的加载逻辑（`FileKey.cpp`）按顺序尝试：XML 格式 → 32 字节二进制 → 64 字节十六进制 → 都不是则取整个文件的 SHA-256
- 也就是说，任意文件都可以作为 keyfile
- 丢失即无法打开，没有恢复途径
- 建议：keyfile 不与数据库放在同一处；若担心自锁风险，可以不用

## 同步方案（若需要）

已讨论的结论：
- Google Drive / Dropbox / MEGA 在部分网络环境下不可靠，需排除
- 首选可直连的 WebDAV 服务（如坚果云）或用 VPS 自建；PC 端需另配同步手段（官方客户端 / rclone / 自写脚本）
- KP2A 原生支持 WebDAV，并支持 Nextcloud 分块上传
- 附件很耗流量（每次全量传输），**不要把附件放进日常同步的库**
