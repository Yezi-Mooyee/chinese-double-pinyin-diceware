# 01 方案决策记录

本文件记录这么设计的缘由，避免重复走已经走过的弯路。

## 需求溯源

起点是手工管理密码：复杂强密码抄写太烦，记在纸上也防不住能接触住所的人。于是需要一个密码管理器，可管理器本身也要有个根密码，保管难题跟纸面记录一样。

核心诉求可以还原成三条：

- 只记一个高熵密码，而不是记几十个网站密码
- 不依赖纸，能防住接触得到住所的人
- 日常解锁不反复输根密码，交给设备的生物识别或短码

## 关键决策

### 决策 1：用中文词表，不用英文 diceware

对非英语母语者，EFF 长词表 7776 词里有大量生词，记住词之外还得记住拼写，负担翻倍。中文是母语，词汇量和语义联想都占优势。

### 决策 2：用词，不用单字

理由与现代汉语本身的性质有关，也与 `cryptogun/diceware` 作者独立得出的结论一致（原文为英文，此处意译）：

> 中文的复合词就像英文单词，但中文的单字就像 a-z。例如北京 = bei/jing，上海 = shang/hai。所以比特币（BIP39）用的那个单字词表不实用。

补充理由：现代汉语读音退化，需要多音节词消歧，纯粹记忆很依赖读音。单字不是现代人的记忆单位。

### 决策 3：输出用自然码双拼

对长期自然码使用者，汉字到键位是技能内化的直达映射（程序性记忆），不必经过全拼。据此输出长度减半，且不增加转换负担。

不要拿「双拼多一层转换」当反对理由，那是新手才有的模型，对熟练用户不成立。

### 决策 4：不依赖前缀码

这是本项目最容易搞错的一点，澄清如下（详见 `02-词表资源.md`）：

- 「唯一可解码」要保证的是「词序列 → 密码串」构成**单射**，能不能让人类反推密码并不重要。若多个词序列映射到同一串，会带来密码空间塌陷，有效熵下降。
- 达到这一目的有三种手段：前缀码（省分隔符，但要排除部分高频词）、加分隔符（最直接）、定长码（双拼加全双音节词表，最干净）。
- 分隔符带来的几个字符不是问题，因此前缀码不是必需的，不要把它当成前提条件来论证。

### 决策 5：不写纸，纯记忆加定期自检

对纸质保管的顾虑是具体的：防不住身边人，也不想为此建立一套物品管理体系。这一点已充分论证，不必再劝。

替代方案是流程性的：

- 初期高频输入以固化记忆
- 定期自检，默背词序列并完整走通「词 → 双拼」链路
- 若自检失败，才考虑启用纸质保险，作为后路保留

> 参考：`cryptogun/diceware` 的作者在 README 里用了更强的措辞，建议设置每月提醒闹钟默背密码，否则「一定会忘记并丢失资料」。

## 已确认的技术结论

| 项目 | 结论 |
|---|---|
| 词表规模 | 8173 词，全为双字词，每词 log₂8173 ≈ **12.997 bit** |
| 推荐词数 | 7 词 → **90.98 bit**，80 bit 以上即足够 |
| 双拼输出长度 | 双字词 4 字母；7 词 28 字母，全小写 |
| 定长性质 | 全双字词 ⇒ 定长码 ⇒ 无需分隔符、无歧义 |
| 单射性实测 | 8173 个双拼码只有 1 组重复（同音词），基本是单射 |
| 规则保密性 | 自然码是公开标准，可查表，写下来不损失安全性 |
| 词表保密性 | 公开无害，唯一秘密是选了哪几个词 |
| 读音依据 | 《现代汉语词典》的读音；上游词表自带的拼音列是唯一来源，其中约 21 处标注错误已逐条修正 |

## 仍需注意

1. 词表质量未经社区审查。两份候选上游词表的 star 数都很低（见 `02-词表资源.md`），需要人工抽查生僻度。
2. 多音字在**词**的层面基本不成问题（「银行」不会被读成 yínxíng），剩下的是声调问题，而双拼输出不带声调。真正要避开的是整词有两种读法、声母韵母又不同的词，这类已经剔除。
