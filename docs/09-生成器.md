# 09 — 生成器

`tools/pick-and-burn.c` 是配套的口令生成器，Windows 专用，C11。

它从词表里随机选词，画成几行候选，让使用者挑一行编成画面记住，再按自然码双拼
打出来。连续打对若干次就算记住。

词表有 8173 个词，每词两个汉字，双拼正好四个字母。七个词是 28 个字母，约 91 bit。

## 编译

    gcc -O2 -Wall -Wextra -std=c11 -finput-charset=UTF-8 -fexec-charset=UTF-8 \
        -o pick-and-burn.exe pick-and-burn.c -lbcrypt

MSVC 需要 `/utf-8`，并自行链接 `bcrypt.lib`。依赖 `BCryptGenRandom`、SHA-256、
`VirtualLock`、`SecureZeroMemory` 和宽字符文件 API，都是 Windows 自带的。

## 用法

    pick-and-burn.exe              默认一次给 4 行，每行 7 个词，连续打对 5 次
    pick-and-burn.exe -g 6 -d 8
    pick-and-burn.exe -l D:\wordlist.txt
    pick-and-burn.exe -h

`-g` 是几行候选，`-n` 是每行几个词，`-d` 是打对几次算过，`-l` 指定词表。

词表格式是 UTF-8 文本，每行「中文词<TAB>四字母双拼码」。默认路径由 exe 自身
位置推导，取上一级的 `wordlist-shuangpin-cg.txt`。

## 自检

    gcc -O2 -std=c11 -Wno-unused-function -finput-charset=UTF-8 -fexec-charset=UTF-8 \
        -o selftest-pick-and-burn.exe selftest-pick-and-burn.c -lbcrypt
    selftest-pick-and-burn.exe

38 项，全过时退出码 0。自检源码里把终端护栏短路了，否则它自己会被拒；它不调用
主程序的 `main`。

## 几个设计决定

### 为什么用 C

Python 里 `str` 是不可变对象。`input()` 拿到的那行口令没法就地擦掉，`del` 之后
字节还留在分配器的空闲池里，要等那块内存被复用。C 里同一块缓冲可以精确控制：
分配、锁定、使用、清零、释放。

### 为什么不能用 memset

本机 gcc 13.2 和 clang 22.1.8 在 `-O2` 下都实测过。缓冲区在 `printf` 之后不再
被使用时，编译器会把 `memset` 连同清零指令一起删掉，函数在 `printf` 后直接
`ret`，不报任何警告。`SecureZeroMemory` 和 volatile 循环都保留了下来。

另外，C11 Annex K 的 `memset_s` 和 C23 的 `memset_explicit` 在这三个编译器上
都不存在，失败形式是链接期的 `undefined reference` 或 `LNK2019`。所以
`secure_memzero()` 是按 Annex K 的语义自己写的。

### 为什么不拼出口令再比对

每一行候选从来没有被拼成过一个完整的串。判定用的是 SHA-256 指纹，候选行和
使用者输入走同一条链，比的是摘要。进程里任何时刻都不存在完整的口令明文。

链的构造是

    h_0 = SHA256("pick-and-burn/chain/v1")
    h_k = SHA256(h_{k-1} ‖ 31 个零字节 ‖ c_k)

每次推进一个字符，喂进去 32 + 31 + 1 = 64 字节，正好一个块，最后一个 feed
立刻触发压缩，块缓冲随即清空。退格靠链的历史，历史里存的是摘要，不可逆。

第三轮评估表明这个构造挡不住能持续读内存的进程：相邻两个状态摆在那里，单步的
未知量只有一个字符，枚举 95 次 SHA-256 就能还原。详见 `redteam/`。

### 输入回显星号

控制台行输入模式下，使用者敲的每个字符都会被 conhost 回显进屏幕缓冲，同一个
会话里的进程可以 `AttachConsole` 加 `ReadConsoleOutputCharacterW` 读走。程序
因此关掉 `ENABLE_ECHO_INPUT`，自己回显成星号。

完全无回显（getpass 那样）也试过。实测下来打错率明显上升，而打错率一高，受伤的
是「靠反复输入把词序列固化下来」这个目标。星号不泄露新信息：候选词本来就列在
屏幕上，词数公开，看一眼就知道是 28 个字母。长度从来不是秘密。

### 独立窗口

清屏序列不可靠，终端可以不理会，Windows Terminal 自己的文本缓冲和 GPU 纹理里
也可能留有余温。程序因此用 `GetConsoleProcessList()` 检查自己是否独占控制台，
不是的话用 `CREATE_NEW_CONSOLE` 把自己重启到独立窗口，原窗口退出。进程退出，
窗口销毁，缓冲随内存消失。

### 护栏

`stdout` 或 `stdin` 不是真终端时拒绝运行，退出码 2。这条挡的是重定向、管道和
被自动化工具捕获的情况，那等同于把口令写进对面的日志。

`-h` 和 `-V` 不受这条限制，它们不产生口令，输出里也没有秘密。

## 已知边界

- 候选词必须显示给使用者看，词到码的映射写在公开词表里。屏幕上的词就是口令本身。
  同一个会话的任意进程都能读走屏幕再查表还原。
- 使用者敲的每个字符都必须被程序接收，逐字符处理会在内存里留下可枚举的状态。
  读一次内存加几百次哈希就能还原。
- `VirtualLock` 只降低内存页被换出到页面文件的概率，不阻止其他进程读取。真正的
  兜底是整卷加密。
- 低级键盘钩子没防，也防不住。
- 崩溃转储没防。

这个工具只在一种环境下成立：这台机器上除了你信任的软件之外，没有别的东西在跑。
做不到就不要在这里生成口令。
