# pick-and-burn.exe 红队评估报告

**目标**：`T:\密码管理\中文双拼diceware\tools\pick-and-burn.exe`（对象：`tools\pick-and-burn.c`，630 行）
**视角**：攻击者 —— 与使用者**同一个 Windows 登录会话、同一个用户、同为 Medium 完整性级别**的另一个普通进程
**权限前提**：无管理员、无 SeDebugPrivilege、无驱动、不注入线程、不修改目标进程
**日期**：本次会话

---

## 0. 结论

C 版在**内存卫生**这件事上做得确实好：`secure_memzero` 生效，我实测在目标进程里只找到 **1 份**密码明文副本（就是 `answer` 缓冲本身），没有出现"擦了一处、漏了三处"的典型翻车。

但这个优势没有转化成安全性，原因有两层：

1. **清零只能缩短窗口期，不能消除窗口期。** `answer` 缓冲必须在整个记忆练习（drills）期间保持明文，清零发生在用户按完回车之后 —— 而用户此刻正拿着这串密码去 KeePassXC 里建库。窗口期不是几毫秒，是几分钟。

2. **真正致命的问题根本不在内存上。** 候选词以明文显示在屏幕上，而「中文词 → 双拼码」是同目录下公开词表里写死的确定性映射。于是：

   > **密码 = f(屏幕内容, 公开词表)**

   攻击者读一次屏幕、读一次词表，就在**用户还没做出选择之前**算出了全部 4 组候选密码。这条路径不碰内存、不嗅探键盘、不需要任何时序配合，也**不会因为把内存清零做得更好而有丝毫改善**。

三条独立路径全部实证成功；并且我特意把攻击者做成**与目标进程毫无关系的独立进程**（由 WMI 服务 `WmiPrvSE.exe` 启动，无派生关系、不继承句柄），以排除"自己人打自己人"的质疑。

**唯一被挡住的情形**：把攻击者降为**低完整性（Low IL）**后，读屏和读内存都返回 `ERROR_ACCESS_DENIED(5)`。这层 Windows 完整性边界是有效的 —— 但它挡不住用户桌面上任何一个普通程序。

## 1. 威胁模型错位

`pick-and-burn.c` 的头注释（第 51–58 行）写得很清楚，防御目标只有一个：

> 绝不要重定向、管道，或由自动化工具（含 AI agent）启动 —— 那等同于把根密码写进对面的日志。

`_isatty` 双重检查（第 508 行）确实拦住了重定向和管道。我实测确认：在 DSH 的 pwsh 工具下运行，退出码 **2**，报"标准输入/输出不是终端"。

**但这个护栏防的是"密码被写进日志/文件"，它完全没覆盖"密码被旁边看着的进程读走"。** 而后者才是同一个交互式桌面上真实存在的威胁：

| 属于"同用户同会话 Medium IL"这个集合的进程 | 举例 |
|---|---|
| 用户主动安装的软件 | 第三方输入法、浏览器、下载工具、游戏 |
| 开发工具链 | VS Code 及其扩展宿主、Node.js、Python 包、Docker Desktop |
| 被钓鱼执行的可执行文件 | 任何用户态、未提权的恶意程序 |
| 供应链污染 | 任何一次 npm/pip 安装带来的 postinstall 脚本 |

这个集合里的进程**不需要任何特权**就能做下面所有事。程序文档里对这一点是空白的。

## 2. 攻击路径与实证结果

### 路径 A —— 读走控制台屏幕（严重）

**原理**：程序从头到尾**没有关闭 `ENABLE_ECHO_INPUT`**。`read_line()` 用的是 `fgets(stdin)`，走的是控制台行输入，用户敲的每一个字符都会被 conhost **回显**到屏幕缓冲。清屏（`ESC[2J ESC[3J ESC[H`）只发生在最后"完成后按回车"那一刻。

于是整段记忆练习期间（几十秒到几分钟），用户敲进去的密码明文就躺在 conhost 的屏幕缓冲里。

**攻击手法**（零权限，不需要附加调试器）：

```c
FreeConsole();                    // 先脱离自己的控制台
AttachConsole(target_pid);        // 附加到目标进程的控制台
CreateFileW(L"CONOUT$", ...);     // 现在 CONOUT$ 指向目标的屏幕缓冲
<REDACTED>(...); // 整屏读走
```

**实测证据**（`evidence/ev-screen2.txt`）：

```
 14 |    第 1/1 次 > <REDACTED>
```

这一行就是使用者敲进 KeePassXC 主密码框的那 28 个字符。

**Windows Terminal / ConPTY 场景同样成立**（已实测）：你用源码注释里推荐的 `wt.exe -w new ...` 启动时，`AttachConsole` 附加到的是 ConPTY 服务端控制台，屏幕内容照读不误。副作用只有一条：窗口太窄时长行会折行，可能读不全某一组候选词 —— 攻击者多轮询几次或等窗口调整即可。

---

### 路径 B —— 屏幕 + 公开词表 = 直接算出密码（最严重，且无法通过改实现来修）

**原理**：这一步不需要任何"攻击技巧"。

- 候选词是明文显示的中文；
- `wordlist-shuangpin-cg.txt` 与 exe 同目录（默认路径就是从 exe 位置推导的，第 299–324 行），攻击者随手可读；
- 词 → 双拼码的映射是**确定的、无盐的**。

所以攻击者只要拿到屏幕上的 7 个词，查表拼接就得到密码。**不需要等用户输入，不需要看用户敲了什么。**

**实测证据**（`evidence/ev-solve1.txt`）——这是在用户还没按任何键的候选界面下算出来的：

```
  候选组 [1]：踌躇 委派 断绝 朗诵 贸易 蓝天 摸索
          → 该组密码：<REDACTED>
  候选组 [2]：上午 塑造 未可 渎职 营造  砖头 操纵
          → 该组密码：<REDACTED>
  候选组 [3]：桂冠 迎合 退缩 整修 忏悔 周末 客商
          → 该组密码：<REDACTED>
  候选组 [4]：一道 均匀 多年 家具 充分 大好 介绍
          → 该组密码：<REDACTED>

>>> 用户在选之前，全部 4 个候选密码就已经被算出来了。
```

**这是设计的固有性质，不是编码瑕疵。** diceware 要求用户必须看到词才能编故事记忆；而只要看到词、且映射规则公开确定，看屏幕就等于看密码。任何"把内存清得更干净"的努力对这条路都无效。

---

### 路径 C —— 读进程内存（严重，且直接推翻 `VirtualLock` 的价值）

**原理**：

```c
HANDLE h = OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, FALSE, pid);
VirtualQueryEx + ReadProcessMemory ...   // 找连续小写字母串
```

同一个用户读同一个用户的进程，内核直接放行。**`VirtualLock` 对此毫无作用** —— 它的语义只是"阻止页面被换出到 pagefile.sys"，和"阻止同用户进程读取"是两件完全无关的事。

**实测证据**（`evidence/ev-mem.txt`）：

```
OpenProcess(PROCESS_VM_READ) 成功 —— 无需管理员，无需 SeDebugPrivilege。
命中 30 段不同的明文：
    1 份副本  000001b9c8de1680  MEM_PRIVATE  len=28  <REDACTED>
```

地址 `...c8de1680` 就是 `locked_alloc()` 分配出来的那块 `answer` 缓冲 —— 被 `VirtualLock` 锁过、被 `<REDACTED>` 抬过配额，`ReadProcessMemory` 照样一次读穿。

**顺带一个好消息**（我原本预期是漏洞，实测不成立，故不列为问题）：我一度怀疑 `fgets` 会在 CRT 的 stdin `FILE` 行缓冲（`_base`，默认 4 KB）里留下第二份副本，而 `read_line()` 只清了调用者的栈缓冲。实测在密码已输入、drills 进行中的时刻扫描，**只有 1 份副本** —— CRT 那份要么被字符设备的读取行为规避，要么被后续读取覆盖。栈清零是真的有效。

## 3. 打不进去的地方（对照实验，避免高估问题）

| 对照 | 结果 | 说明 |
|---|---|---|
| `_isatty` 护栏 | **有效** | 管道/重定向下退出码 2，拒绝运行 |
| `secure_memzero` 栈清零 | **有效** | 实测仅 1 份副本，无意外扩散 |
| 低完整性（Low IL）攻击者读屏 | **被挡住** | `AttachConsole` → `ERROR_ACCESS_DENIED(5)` |
| 低完整性（Low IL）攻击者读内存 | **被挡住** | `OpenProcess(VM_READ)` → `ERROR_ACCESS_DENIED(5)` |
| 低完整性攻击者枚举进程 | **被挡住** | Toolhelp32 快照看不到目标进程 |

我特意加了降权模式（`attacker.exe low <子命令>`，把自身令牌的完整性级别改写成 Low RID `0x1000`）做了这组对照。结论是：**Windows 的完整性边界在这一层是有效的**，一个被真正沙箱化的进程拿不到这些东西。

**但这不构成安慰**，因为：

- 攻击者要落入"Medium IL"太容易了 —— 用户登录后运行的一切未提权程序都在这个级别；
- 反过来，用 Low IL 挡住攻击者，意味着**只有把使用者自己关进沙箱才行**，而使用者的终端本身必须是 Medium IL 才能正常用。

## 4. 关于"两个权限互不相干的进程"

为了排除"攻击者其实是从目标派生出来的，所以不算第三方"这个质疑，本次评估的攻击者满足：

- **由 WMI 服务启动**：`Invoke-CimMethod Win32_Process Create` → 攻击者进程的父进程是 `WmiPrvSE.exe`，与目标进程、与启动目标的那个 PowerShell **没有任何派生关系**；
- **不继承任何句柄**：不与目标共享控制台句柄、内存句柄或任何对象；
- **权限上下文互不继承**：目标由 `CREATE_NEW_CONSOLE` 独立创建，攻击者由服务创建，两者之间只有"同用户同会话"这一条共性 —— 而这一条恰恰是无法避免的。

在这个设定下，路径 A/B/C 全部成功（见第 2 节证据）。所以这些攻击**不需要攻击者与目标有任何关系**。

## 5. 未实测、但按机制预期成立的补充路径

以下几条我没有实测（成本或环境限制），但机制上成立，列出来是因为它们决定了"修补到什么程度才算够"：

1. **低级键盘钩子**：同会话进程用 `SetWindowsHookEx(WH_KEYBOARD_LL)` 记录全部按键，不需要管理员。用户敲的双拼码会被完整捕获。这条路径完全绕开"用户是否看得见屏幕"的问题，也是路径 A 关掉回显之后仍然存在的残余风险。
2. **Windows Terminal 进程内存**：即使 `ESC[3J` 清掉了 conhost/ConPTY 的回滚缓冲，`WindowsTerminal.exe` 自己的文本缓冲区、GPU 纹理里可能仍留有历史文本。攻击者读 `WindowsTerminal.exe` 的内存即可。
3. **屏幕截图 / OCR**：密码回显期间整屏截图，纯小写等宽字符的识别成本极低。
4. **pagefile 残留**：`answer` 被 `VirtualLock` 了，但 `locked_alloc()` **忽略了 `VirtualLock` 的返回值**（第 122 行 `(void)VirtualLock(p, n);`）。工作集配额不足时它会静默失败，而程序不会有任何提示 —— 此时密码可能随页面换出落到 `pagefile.sys`（无 BitLocker 时是可读明文）。这条只在未启用整卷加密时才有意义。
5. **崩溃转储**：drills 期间若因任何原因产生 WER 转储，明文会进入转储文件。

## 6. 修复建议

按"实际收益 / 成本"排序。**注意第 1 条是唯一能真正解决问题的方向，但它需要重新审视方案本身。**

### 6.1 接受"屏幕即密码"，并据此重设威胁模型（治本）

必须承认一件事：**在当前设计下，能让攻击者读到屏幕，就等于把密码给它了。** 所以：

- **最低限度**：在程序的启动横幅和头注释里明确写出这一条。现在文档只警告了"重定向/管道/自动化工具"，这会给人"只要不在管道里跑就安全了"的错觉。建议加一句：

  > 本程序**不防**同机同用户的其他进程。如果这台机器上运行着你不信任的软件（第三方输入法、来路不明的工具、刚装完的 npm 包……），不要在这里生成根密码 —— 换一台干净的机器。

- **真正的对策**：把"生成 + 录入"放到一个可信环境里。可选：
  - 一台离线、干净、运行期间不装任何不可信软件的机器；
  - 一个专用的、只有基本系统组件的 Windows 账户 / 虚拟机（注意：同一会话里仍然不安全，必须是**另一个不与日常使用混用的环境**）；
  - 或者干脆不在本机做这件事。

- ~~可以考虑降低"泄屏即失守"的严重性：让屏幕上的信息不足以唯一确定密码……~~
  **这条建议是错的，已收回。** 理由见 [`fix-plan.md`](fix-plan.md) 第 1 节：
  密码必须被用户知道，用户获取密码的唯一通道就是这块屏幕；屏幕信息一旦不足，
  用户自己也就确定不了密码，除非用户从屏幕之外再贡献一段额外秘密 ——
  而那正是本工具"零记忆负担"的设计目标要消除的东西。这条路自相矛盾，
  不存在中间的可行点。

### 6.2 关闭控制台回显（必做，改动极小，收益明确）

程序本来就只回 `✅ 正确` / `❌ 不匹配`，**从不显示答案**，所以关掉回显对可用性没有任何损失，反而更贴合"用后即焚"的原意：

```c
HANDLE hin = GetStdHandle(STD_INPUT_HANDLE);
DWORD  mode;
if (GetConsoleMode(hin, &mode)) {
    SetConsoleMode(hin, mode & ~ENABLE_ECHO_INPUT);
}
```

（仍然要自己处理行编辑/退格的视觉反馈，或者接受"看不见自己打了什么"——考虑到 drills 的目的就是盲打记忆，这其实是**更贴合训练目标**的行为。）

这一条只堵住路径 A 的一半（用户输入回显），**堵不住路径 B**（候选词显示）。

### 6.3 提前并反复清屏

现在只在最后按回车时清屏。建议：

- drills 每次输入结束后立刻 `burn_screen()` + 清回滚；
- 关闭回显后，屏幕缓冲里不再有输入行，清屏只需覆盖候选词。

仍然只对路径 A 有意义。

### 6.4 缩短明文窗口期（真实的实现改进）

`answer` 缓冲从 `concat_codes()` 一直留到程序退出。但 drills 通过之后它**已经没用了**，而用户接下来要去 KeePassXC 输密码，可能停留几分钟。建议：

```c
if (!run_drills(answer, drills)) {
    secure_memzero(answer, answer_cap);   /* 放弃这一组也别留着 */
    continue;
}
/* 打对之后立刻销毁，别等程序退出 */
printf("   ✅ 已连续打对。\n\n");
...  /* 提示文字打印完 */
secure_memzero(answer, answer_cap);
```

`cands`（选中词的索引数组）同理 —— 它虽然不是明文，但配上公开词表同样能还原密码，也应该在选组完成后立即清零。

### 6.5 别把 `VirtualLock` 当成安全措施

`locked_alloc()` 应当检查返回值，并且在注释里讲清楚：`VirtualLock` 防的是**换页到磁盘**，不是**同用户进程读取**。目前头注释里把它摆在"内存安全"的位置，容易造成错误的安全感。

### 6.6 不要在这条链上长时间保留同一串密码

程序第 2 步让用户把同一串 28 个字母作为 KeePassXC 主密码输入。这意味着：

- 这串密码从"一次性练习材料"变成"每次解锁都要输入的长期秘密"；
- 攻击窗口从"drill 那几十秒"变成"**每一次解锁**"；
- 打错重来的那张截屏、那次剪贴板、那个输入法词库，都会长期留存。

值得在文档里提醒：如果威胁模型里包含本机进程，那么这串密码从输入 KeePassXC 的那一刻起就已经暴露了 —— 而它偏偏是最不该暴露的那一个（根密码）。
