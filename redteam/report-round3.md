# 第三轮红队报告 —— 链式哈希的历史可被枚举反推

**目标**：`tools\pick-and-burn.c`（第三版，含「链式逐字符哈希」整改）
**依据**：`09-红队整改与复验.md`（本次更新版）
**约束**：本轮**不使用读屏幕**这条路径 —— 按 `09-` 第 9 节第 4 条，屏幕设防已放弃
**威胁模型**：同用户、同会话、Medium 完整性的普通进程；无管理员、无 SeDebug、不注入线程

---

## 0. 结论

第二轮报的 `line[]` 明文窗口**确实修好了**，我用 `round2-verify.ps1` 复验过，第 3/4/5 步全部由「命中」变成「否」。

但用来替代它的**链式哈希**没有达成它的设计目标。设计目标写得很清楚（源码第 669–673 行）：

> · 当前字符在块缓冲里的寿命是亚微秒；
> · `h_{k-1}` 是散列值，读走也推不出任何明文；
> · 内存里任何时刻最多存在 **1 个** 明文字符。

前两条成立，第三条在字面上也成立。但问题在于 —— **`h_{k-1}` 读走推不推得出明文，取决于每一步的输入空间有多大**。

这条链是：

```
h_0 = SHA256("pick-and-burn/chain/v1")
h_k = SHA256( h_{k-1} ‖ 31 个零字节 ‖ c_k )        c_k 是 1 个字符
```

每步只推进**一个字符**，取值空间是 95 个可打印 ASCII。所以给定相邻的两个状态，`c_k` 是**唯一可枚举**的：

```
for c in 0x20..0x7e:
    if SHA256(h_{k-1} ‖ 0^31 ‖ c) == h_k   →   c_k = c
```

95 次 SHA-256，微秒级。而 `chain.h` 里**完整保存着 h_0..h_k 的全部历史** —— 退格要靠它（`chain_pop()` 只是 `len--`）。

**于是整条历史 = 明文密码的可解码表示。** 攻击者读一次内存、跑一遍枚举，就拿到了使用者敲进去的每一个字符。

实测（全程不读屏幕、不装键盘钩子、不 `AttachConsole`，只要一次 `OpenProcess(PROCESS_VM_READ)`）：

| 场景 | 攻击者输入 | 结果 |
|---|---|---|
| 使用者打任意串（未回车） | 只读内存 | **恢复出 `<REDACTED>`，28/28 字符全对** |
| 使用者打**对**密码、达标、去建库 6 秒后 | 只读内存 | **恢复出 `<REDACTED>`，28/28 字符全对** |

## 1. 攻击原理

### 1.1 链的每一步都是可枚举的

`chain_step()`（源码第 692 行）的输入构造是确定的：

```c
hasher_feed(&H, prev, HASH_LEN);   /* 32：已知，就在内存里 */
hasher_feed(&H, Z31, sizeof Z31);  /* 31：全零常量，源码里写着 */
hasher_feed(&H, &c, 1);            /*  1：唯一未知量，却只有 95 种可能 */
```

`prev` 和 `Z31` 都是攻击者已知或可读的，唯一未知的 `c` 只有 95 个取值。这不是"破解哈希"，这是**查表**。

### 1.2 整条历史都在内存里，而且是连续的

```c
typedef struct {
    unsigned char (*h)[HASH_LEN];   /* 一块连续内存，cap 个 32 字节状态 */
    size_t        cap;
    size_t        len;
} Chain;
```

`chain.h` 由 `locked_alloc()` 分配，`chain_cap = words*4 + 32`（默认 60 个状态）。`VirtualLock` 只防换页、**不防 `ReadProcessMemory`**（第一轮已实测）。

### 1.3 攻击者如何定位这条链

`h_0 = SHA256("pick-and-burn/chain/v1")` 是**程序里的固定常量**，域名字符串直接写在源码里，攻击者当然算得出来：

```
9c99e2d336d5c15b819076301c03cf7ee57feb8e49f3124290a87553b5ec4ef9
```

在目标进程内存里搜这 32 字节，命中的位置就是 `chain.h[0]`。往后的 32 字节一块就是 `h_1`、`h_2`……

（**顺带说明**：就算把 `h_0` 改成每次运行随机，也不解决问题。攻击者可以直接扫描内存里那些高熵的 32 字节块，对每一对相邻块跑一次 95 次的枚举测试 —— 满足关系的就链在一起。定位难度从"搜一个常量"变成"多做几百万次哈希"，仍然是秒级的事。）

### 1.4 生命周期比上一轮的 `line[]` 更长

- `chain_reset()` 只在 `read_secret_chain()` 开头调用，而且**只重置 `h[0]` 和 `len`，不清 `h[1..]`** —— 旧数据留在数组里。
- `secure_memzero(chain.h, ...)` 出现在源码第 1262 行，即**程序退出前**。
- 使用者达标之后，程序进入「等他按回车销毁」的等待态（第 4.2g 条）；**这段时间链完全没有被清理**。而使用者此刻往往已经切去 KeePassXC 建库了。

所以暴露窗口是：**从使用者敲下第一个字符，一直到程序退出**。上一轮 `line[]` 的窗口是「到按回车为止」，这一版反而把窗口拉长了。

## 2. 为什么这一步没有达成设计目标

设计者显然认真考虑过"哈希内部块缓冲会攒明文"这件事（`09-` 第 5.2 节把这一点写得很清楚），并因此放弃了「逐字符喂 + 最后 FinishHash」的方案，改成"每步喂满 64 字节立即压缩"。

这个推理链条里唯一缺的一环是：

> **明文没有被保存在内存里，不等于明文不能被从内存里恢复出来。**

单向函数的安全性来自**搜索空间足够大**。把 28 个字符一次性哈希，空间是 26^28；但把每个字符单独推进一次哈希、并把每一步的中间状态都留着，搜索空间就塌缩成 **26 —— 每个字符一次**。

用一个比喻：这相当于把保险箱的钥匙熔掉做成一把新钥匙，然后把**每一步锻造的模具**整整齐齐摆在桌上。钥匙确实找不回来了，但照着模具能一模一样的配出来。

## 3. 这个问题的根本性

这不是"实现写漏了一行"，而是**逐字符增量验证这个模型本身的性质**。把选择列全：

| 方案 | 问题 |
|---|---|
| 用户输入攒进缓冲，回车后一次性哈希 | 缓冲里是明文 —— 就是第二轮的 `line[]` 漏洞 |
| 逐字符推进哈希，**保留历史**（当前做法） | 历史里每一步都可枚举 —— 本报告的漏洞 |
| 逐字符推进哈希，**只保留当前状态**（不保存历史） | 攻击者仍可高频轮询：使用者按键间隔约 100 ms，而扫描一次 8 MiB 只要几十毫秒；若只监视那 32 字节的固定地址，采样可以做到微秒级，几乎不会漏。漏掉一两步也只是把枚举空间从 95 变成 95²，仍可解 |
| 给每一步加盐，让单步不可枚举 | 盐必须能被程序自己重现（否则无法与候选行比对），因而必然存在于内存中或可从二进制提取 —— 攻击者知道盐，照样枚举 |
| 让中间状态"存在但不可读" | Windows 用户态没有这种内存；跨进程保护（PPL 等）需要签名，本程序用不上 |

**结论**：在"同用户进程可以任意读目标内存"这个威胁模型下，**逐字符的密码输入环节无法做到内存安全**。这不是本程序写得不好，是这个模型没有解 —— 和路径 B（候选词必须显示给使用者看）属于同一类：**必须给人看 / 必须被程序逐字符接收的信息，在屏幕层面和内存层面都无解**。

区别只在于代价：路径 B 是"看一眼屏幕"；这一条是"读一次内存 + 跑 95×28 次哈希"。**对攻击者来说两者都是零成本。**

## 5. 加固建议（及其限度）

先说限度：**第 3 节已经论证过，在当前的威胁模型下没有根治方案。** 以下措施只是提高门槛，不要把它们当作修好了。

### 5.1 立刻可做：别保存历史

把退格从「`len--`」改成「清空整行重打」，`chain.h` 只保留**当前状态**一份。

- 好处：攻击者一次读取只能拿到一个 `h_k`，要跨步就得枚举。**从"一次读取 = 全部密码"变成"必须连续监控、一次都不能漏"。**
- 代价：使用者按退格要重打整行。考虑到关回显之后本来就没有行编辑反馈，这个代价未必不能接受。
- **但它挡不住有耐心的攻击者**：按键间隔远大于一次内存扫描的耗时，轮询可以跟上。

### 5.2 顺手可做：`chain_reset()` 应该清干净

```c
static void chain_reset(Chain *C)
{
    chain_init(C->h[0]);
    C->len = 0;          /* 只动这两个，h[1..] 里是上一轮的全部历史 */
}
```

建议改成 `secure_memzero(C->h, C->cap * HASH_LEN)` 之后再 `chain_init(C->h[0])`。这不解决根本问题（当前这一轮的链还在），但能消掉"上一轮残留"，代价几乎为零。

### 5.3 更值得考虑的：改变"必须逐字符验证"这个前提

既然内存安全做不到，那就让密码**不要在这台机器的内存里以任何可恢复形式出现**。可能的形态：

- 生成与录入都在可信环境完成（与路径 B 的建议一致 —— `09-` 第 9 节已决定不再为屏幕投入，内存这条同理）；
- 或者接受它，并在**启动横幅**里把话说全：现在的横幅只说了"屏幕上的词 + 公开词表 = 密码"，建议补上"**你在输入框里敲的每一个字符，也会以可枚举的形式留在进程内存里，直到窗口关闭**"。

### 5.4 不建议的方向

- **不要**试图用"更长更复杂的链"（比如每步喂入位置、喂入随机前缀）来加固 —— 只要单步的未知量仍是一个字符，枚举成本就在 95 次哈希这个量级。
- **不要**把这次的修复理解成"再加一层哈希就好了"。问题的性质是**信息论层面的**：内存里存在足以唯一确定明文的可枚举状态，它就等价于明文。

## 6. 公开漏洞对照

| 公开漏洞形态 | 代表案例 | 本程序现状 |
|---|---|---|
| 输入缓冲 / 前缀在内存中残留 | [KeePass CVE-2023-32784](https://security-tracker.debian.org/tracker/CVE-2023-32784)（[利用与缓解分析](https://github.com/areebashoaib42/KeePass-CVE-2023-32784-Exploitation-and-Defense)） | **第二轮已修**（`line[]` 窗口消失） |
| 中间状态可枚举，等价于明文 | 迭代哈希的"可转移状态"分析（Transferable State Attack on Iterated Hashing Functions, exploit-db #20119） | **本轮漏洞** —— 见第 1 节 |
| 长期驻留的明文副本 | 通用 | 已修（无 `answer`） |
| 剪贴板被其他进程读取 | 大量密码管理器 | 不适用（不碰剪贴板） |
| 弱随机源 | Debian OpenSSL CVE-2008-0166、PHP `rand()` | 已防（`BCryptGenRandom` + 拒绝采样） |
| 安全清零被优化掉 | 通用 | 已防（`SecureZeroMemory`，源码内有汇编级实测） |
| 屏幕 / UI 侧信道 | 键盘记录器、屏幕抓取 | **已放弃设防**（`09-` 第 9 节第 4 条） |
| 低级键盘钩子 | 通用 | 未防（已知边界第 3 条） |
| 页面文件残留 | 通用 | 部分（`VirtualLock` 只防换页，不防读取） |
| 崩溃转储 | 通用 | 未防 |

**两类漏洞的对照很有意思**：KeePass 那个是"明文直接躺在内存里"，本轮这个是"明文被换了一种编码躺在内存里"。后者的隐蔽性更强 —— 静态审计看到的是"只存了 SHA-256 摘要"，只有在算过每一步的输入空间之后，才会发现那实际上是一张**逐字符的查找表**。
