# 第二轮红队报告 —— 针对整改后的 pick-and-burn.exe

**目标**：`tools\pick-and-burn.c`（整改版，1169 行，2026-10-01 22:58 构建）
**依据文档**：`09-红队整改与复验.md`、`redteam/report-redteam.md`
**复现脚本**：`redteam/round2-verify.ps1`　**原始证据**：`redteam/evidence-round2/`
**威胁模型**：与目标同用户、同会话、同为 Medium 完整性的普通进程 —— 无管理员、无 SeDebug、不注入线程

## 0. 结论

整改**确实有效**：旧版那个长期驻留的 `answer` 缓冲被彻底消除了，我实测确认"用户还没输入时，进程里找不到任何完整明文"。指纹替代、`cands` 画完即抹、关闭回显，这几项都按设计生效。

但**密码仍然被拿到了**，而且这次是靠一条全新暴露出来的路径：

> `read_secret()` 把使用者敲的字符逐个累加进 `line[LINE_MAX_]`，
> 而这块栈缓冲**要等到使用者按下回车之后才被清零**。
> 所以明文驻留的窗口不是"毫秒级"，而是**使用者从敲第一个键到按下回车的整个期间**。

实测：使用者在输入过程中，攻击者用一次普通的 `ReadProcessMemory` 就取到了完整密码，**8 秒后仍在**；按下回车后才消失。

这条路径绕过了新版的所有改进：不读屏幕（关回显无效）、不用指纹（不涉及）、不用 `cands`（早已抹掉）。它只需要 `OpenProcess(PROCESS_VM_READ)`。

**另外**：新版把"销毁"刻意推迟到使用者按回车那一刻，而使用者达标后往往直奔 KeePassXC 去建库 —— 这让路径 B（屏幕 → 词表 → 密码）的暴露窗口比整改前**更长**，不是更短。

## 1. 整改生效的部分（逐项实测）

| 整改项 | 实测结果 | 证据 |
|---|---|---|
| 消除 `answer` 长期明文缓冲 | **生效** | 用户未输入时扫描，找不到完整明文 |
| 用 SHA-256 指纹替代明文比对 | **生效** | 长期驻留的只有 32 字节不可逆摘要 |
| `cands` 画完屏立刻抹除 | **生效** | 选组后扫描不到索引数组配出的密码 |
| 关闭 `ENABLE_ECHO_INPUT`，回显成 `*` | **生效** | 屏幕上只有 `*`，读屏拿不到输入内容 |
| BCrypt 哈希对象是否残留明文 | **无残留** | 4 行候选各算过一次指纹后扫描，未发现密码 |
| 低完整性攻击者 | **被挡住** | 沿用上一轮的 `low` 对照，`ERROR_ACCESS_DENIED(5)` |

BCrypt 那一条我专门验证过：流式喂 SHA-256 时，未满一个块的数据本该留在哈希上下文里，而 `BCryptDestroyHash` 会不会清零是实现细节。实测结果是**清零了**，没有残留。这一项做得比预期好。

## 2. 【严重】新发现：输入缓冲的明文窗口

### 2.1 机理

```c
static void read_secret(char *buf, size_t cap)     /* 第 536 行 */
{
    ...
    for (;;) {
        ...
        if (ch >= 0x20 && ch < 0x7f && n + 1 < cap) {
            buf[n++] = (char)ch;                   /* ← 明文逐个累积 */
            buf[n]   = '\0';
            fputc('*', stdout);                    /* 屏幕上只留星号 */
        }
    }
}
```

调用点（第 1081–1109 行）：

```c
read_secret(line, sizeof line);
... 转小写 ...
fingerprint_line(line, fp_in);
secure_memzero(line, sizeof line);                 /* ← 到这里才清零 */
```

关键在于：**`read_secret()` 只在读到回车时才返回**。在它返回之前，使用者敲进去的每一个字符都逐个累积在 `line[]` 里，而这块缓冲在整个输入过程中不会被清、也不会被覆盖。

于是明文驻留时间 = `f(使用者打字速度, 他按回车前的犹豫时间)`，典型值**数秒到十几秒**；而 `drills` 默认 5 次，等于一轮练习里有 5 个这样的窗口。

### 2.2 这与公开漏洞的形态一致

KeePass 的 **CVE-2023-32784** 是同类问题的著名案例：主密码在内存里以"字符前缀"的形式散落（.NET 的 `TextBox` 每次按键生成新字符串，旧的没被清理），攻击者从内存转储中收集这些前缀即可重建主密码。

本程序是它的**更集中版本**：只有一个累积缓冲，不是散落的前缀 —— 攻击者拿到的直接就是完整明文，连拼接都不需要。

### 2.3 实测证据（`evidence-round2/`）

目标 PID 14476，第一行密码 `<REDACTED>`（28 字符）。

| 步骤 | 操作 | 结果 |
|---|---|---|
| 02 | 使用者**还没敲任何键** | `含完整密码: False` —— 整改生效 |
| 03 | 使用者敲了 **14 个字符**，未按回车 | **命中 `yspniafhnmytho`**（`000000cefbffd360`，MEM_PRIVATE） |
| 04 | 敲满 **28 个字符**，未按回车 | **命中完整密码 `<REDACTED>`** |
| 05 | 再等 **8 秒** | **仍然命中** —— 窗口确实很长 |
| 06 | 按下回车 | 命中消失 —— 程序确实清零了 |

攻击命令就是普通的一次内存扫描，没有任何时序技巧：

```
attacker.exe mem <pid> 24
```

### 2.4 为什么它比"读内存"本身更值得重视

- **地址固定**：同一次运行内，`line[]` 始终在同一个栈地址（实测两次扫描都是 `000000cefbffd360`）。攻击者确定地址后，只需反复读取 512 字节 —— 开销极小，可以做到微秒级轮询，**基本不可能漏掉**。
- **不需要读屏**：关掉回显对它无效。
- **不需要 AttachConsole**：纯 `ReadProcessMemory`，连控制台都不用碰。
- **不干扰使用者**：读内存不产生任何副作用。

### 2.5 文档里的一处错误描述

`09-红队整改与复验.md` 第 6.4 节的复验表写着：

> drills 进行中内存里有完整明文串 | 有（`answer`）| **没有**（只有用户刚敲的那一行，**毫秒级窗口**）| 已修

实测与这句不符：那是**秒级**窗口，不是毫秒级；而且它不是"刚敲的那一行"，而是**从第一个字符起就在累积**。这条需要在文档里更正 —— 否则下一轮会有人以为它已经解决了。

## 3. 仍然成立、且这一版把窗口拉长了的：路径 B

路径 B 无法通过改实现消除（原因已在 `report-redteam.md` 与 `09-` 第 3 节论证过），本次只需确认并补充一点。

**确认**：`evidence-round2/01-solve.txt` —— 使用者还没做任何选择，4 组候选密码已经全部算出。

**新问题**：新版第 4.2g 条刻意把销毁动作推迟到使用者按回车：

```c
if (finished || quit) {
    /* 刻意不清屏：让使用者还能再看一眼那些词。 */
    fputs(ESC_RESTORE, stdout);
    ...
    printf("   按回车 → 清内存、清屏、关窗口 : " ...);
```

而使用者达标后的下一步是打开 KeePassXC 建库（提示文字自己就这么写的，见第 2 步）。他很可能是**先去 KeePassXC 把库建完，才回来按回车**。这段时间里，一个开着候选词的窗口就一直摆在屏幕上。

对比：上一轮红队打的补丁是"达标后立刻清屏"，本次改成了"按回车才清"。**从攻击面看这是退步** —— 暴露窗口从"drills 结束"延长到了"使用者想起回来按回车为止"，可能是几分钟甚至更久（他要是切走了没回来，窗口就一直留着）。

这不是 bug，是一个明确的取舍。但既然要取舍，就得知道代价：那 7 个词在这段时间里就是密码本身。

## 4. 实测失败的尝试（诚实的负面结果）

不是所有理论路径都走得通。以下两条我实测后**否掉了**，写出来是为了避免下一轮重复投入。

### 4.1 `PeekConsoleInput` 偷窥按键 —— 机制有效，但抢不过

**理论依据**：新版用 `ReadConsoleInputW()` 逐字符读密码，意味着使用者按下的每个键都会先作为一条 `KEY_EVENT` 进入控制台输入队列。而 `PeekConsoleInput()` 可以查看队列却**不移除记录** —— 程序照样读得到，攻击者也能看到同一批按键。这条路径的诱人之处是：关回显、缩短 `line[]` 窗口，对它都无效。

**对照实验（机制是成立的）**：拿一个不读输入的进程（`ping -n 30`）当靶子，攻击者忙轮询：

```
轮询 5791 次，捕获 16 个按键：
  peek-control-abc          ← 一个不漏
```

**真实目标**：同一个偷窥者对着 pick-and-burn：

```
轮询 19203 次（忙轮询），捕获 0 个按键：
```

**原因**：目标阻塞在 `ReadConsoleInputW()` 上，conhost 记录入队时直接唤醒它，记录在队列里的存活时间是**微秒级**；而 `PeekConsoleInput` 是一次跨进程调用，实测每次约 0.3–0.55 毫秒（9 秒只跑出 16328 轮）。两者差两三个数量级，抢不到。

我还试过用忙轮询（不让出 CPU）提高频率，结果**更差**（19203 次 vs 让出 CPU 的 36881 次）—— 大概是忙循环和控制台内部的锁相互争抢，把双方都拖慢了。

**结论**：这条路径不可用。**但要注意它的前提是真的** —— 一旦将来有人把 `line[]` 的窗口修掉，而程序仍然用 `ReadConsoleInput`，那么攻击者可以改用"抢读"（`ReadConsoleInput` 而非 `Peek`）来与程序瓜分按键。抢读会干扰使用者（他会发现自己老是打不对），但能拿到相当比例的字符。所以修 `line[]` 时不要把这条路径当作已经堵死。

### 4.2 BCrypt 哈希对象残留 —— 未发现

`fingerprint_line()` / `fingerprint_row()` 把明文喂进 SHA-256，而 SHA-256 未满一个块（64 字节）的数据会留在哈希上下文里。28 字节的密码正好不会触发任何块处理，**整个密码都在那个缓冲里**。如果 `BCryptDestroyHash` 不清零，这就是一处持久残留。

实测（`02-mem-before-input.txt`）：4 行候选各算过一次指纹之后扫描，**未发现任何密码明文**。CNG 在销毁哈希对象时做了清零。

## 6. 修复建议

第 6.1 是本次唯一需要动代码的地方；6.2、6.3 是取舍和文档问题。

### 6.1 让明文不落在大缓冲里

目标：把"一个 512 字节缓冲累积整个密码"变成"内存中任何时刻都不存在连续明文"。

**思路**：不要先攒后哈希，而是**每读到一个字符就立刻喂进哈希状态**，字符本身用完即弃。

```c
/* 读一个字符 → 立即喂 → 局部变量马上失效，不做累积 */
if (ch >= 0x20 && ch < 0x7f) {
    hasher_feed(&H, &ch, 1);
    ch = 0;
    fputc('*', stdout);
}
```

**但有两个坑必须一起解决，否则等于没修**：

1. **SHA-256 的块缓冲会替你攒。**
   只喂字符不清缓冲的话，明文会原封不动地累积在 BCrypt 哈希上下文里（最多 63 字节），攻击者照样能一次读走。
   对策：**预填充对齐到 64 字节块**。密码长度是 `words * 4`，程序事先知道；在开始读之前先喂 `(64 - (words*4) % 64) % 64` 字节的固定填充，那么使用者打满最后一个字符时刚好凑满一个块，SHA-256 立即处理并清空缓冲。
   候选行的指纹也要用同一套填充，保证两边一致（否则判定语义就变了 —— 这正是自检第 10 项在守的东西）。
   边角情况：使用者打多或打少时仍会有残留，但残留的不是密码本身。

2. **退格无法回退哈希。**
   用户按 `VK_BACK` 时需要撤销上一个字符，而 SHA-256 不可逆。
   对策：每读一个字符前，用 `BCryptDuplicateHash()` 把当前哈希状态复制一份压栈；退格时弹出恢复。栈里存的是**哈希状态（不可逆）**，不是明文。
   代价：`words*4` 份哈希状态，每份几百字节，合计几 KB —— 可以接受。
   更省事的替代：**不允许退格**（打错就整行重打）。考虑到关回显之后本来就没有行编辑的视觉反馈，这个取舍未必不可接受。

3. **`q` / `n` 两个命令需要识别。**
   只存哈希就认不出"用户输入的是 q 还是 n"了。
   对策：单独保留**前 1–2 个字符**的明文用于命令判定，其余不进任何缓冲。这样最坏情况下内存里只有 2 个字符，无意义。

**这套改法能把"一次读走完整密码"降级为"需要在极短窗口内逐个捕获 28 个字符"**，与路径 B（读屏即得密码）相比是数量级的差距。

**要说清楚的边界**：它只挡"能读内存、读不到屏幕"的攻击者。能读屏幕的照样一眼看穿。

### 6.2 重新考虑"按回车才销毁"（第 4.2g 条）

现在的取舍是"让使用者还能再看一眼"，代价是密码在屏幕上多留几分钟。建议至少改成：

- 达标后**立刻清掉那 7 个词**（清屏或用一个不含秘密的画面覆盖），但把"接着做"的提示留在屏幕上；
- 使用者需要的不是"再看一眼"，而是"记住的节奏已经形成了"—— 他刚连续打对 5 次，此刻正该靠记忆去 KeePassXC 里输入。

如果坚持保留词，那就在提示里明确写出来，例如：「**这 7 个词＝你的密码，它们会一直显示到你按回车。现在就去 KeePassXC 输入，回来立刻按回车。**」

### 6.3 更正文档

`09-红队整改与复验.md` 第 6.4 节表格里"毫秒级窗口"那一格需要改成实测结论（秒级、从第一个字符起累积），否则下一轮复验会继续把它当已修项跳过。
